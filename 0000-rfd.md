## API structure

The `kind` cluster will set up a `service` that exposes the API via a
`gateway`.  This should allow one to hit the service using a developer
browser at a loopback address.

| Method | URI | Description
| ------ | --- | -----------
| GET | / | Project root page.  Browser friendly, used while developing.
| GET | /_heartbeat | A page that prints OK if the service is alive
| GET | /version | A page that contains the application version
| GET | /list | List available Kubernetes namespaces and deployments
| GET | /list?ns=namespace | List available Kubernetes deployments in a
                             specific namespace
| GET | /deployment?name=name&ns=namespace | Get the Kubernetes Deployment
                                           replica count.  Omitting `name`
                                           will report all deployments
                                           within namespace.  Omitting the
                                           `ns` will report deployments in
                                           all namespaces.
| PUT | /deployment?name=name&ns=namespace&replicas=N | Set the number of
                                           Kubernetes Deployment replicas.
                                           The `name` and `ns` arguments are
                                           required.

## Caching

The `/list` and `GET /deployment` responses can be cached.  Caching is done
in the application memory.  This means that with multiple instances it is
possible to get inconsistent responses. Inconsistency should be reasonably
unlikely due to the cache invalidation that is triggered by k8s deployment
watch.

Cache is populated at startup, and requestes are always served from cache
for maximum responsiveness.  While cache is populated liveliness endpoint
will not mark pod ready.

## Pod Lifecycle

The application will implement a `/_heartbeat` status page that will inform
Kubernetes if the application has fully started, and is still running.  This
allows adding lightweight `livenessProbe` and `readinessProbe` to the
deployment.

Apart from having a status page, there is a need for `restartPolicy: Always`
to have better change for no disruptions to service if and when something
minor goes wrong.

Updates will use the `RollingUpdate` strategy to avoid upgrade related
disruptions and allow a smooth rollback if and when the next version turns
out to be suboptimal.

## TLS Configuration

The `kind` cluster is assumed to be capable of providing
[SPIFFE](https://medium.com/@nishant.apatil3/spiffe-spire-federation-implementation-on-kind-clusters-d5f3b7c4c062)
certificates for mTLS authentication.

If SPIFFE turns out to be too hard to get working, then certificates will
be managed externally.  In short, this means having a bit of cert tooling in
the deployment tooling that will ensure cfssl or openssl mTLS cert creation,
and usage in the ingress.

Unless technical blockers arise, the cipher suite will be TLS 1.3 with
Ed25519 certificates.

## Workflow

### How to contribute

Use `git remote -v` to see where you cloned the repository.  Use GitHub for
bugs and pull requests.  If the contributions address a vulnerability that
must be kept confidential, please use the `git format-patch main..your-branch`
tooling to attach these changes as an email sent to the upstream maintainer(s).

### Building and testing

Run `make build` or `make test`.  Running `make` without argument(s) will
output the make targets.

## Releasing

Run `make release`.

Running `make release` will:

1. Create annotated git tag.
2. Build the application image.
3. Request the local `kind` k8s cluster to perform update.

Please note that running a release does not mean it will succeed.  One
must look for possible make failures, and keep an eye on service health.

## Observability

The application will write structured logs, that can be seen in stderr.
These logs can be easily fed to Elasticsearch or such.  Notice that
configuration file has loglevel setting.

There is also Prometheus endpoint, that uses prefix `teleport` for the
application specific metrics.  Primary use of these metrics is to have easy
way to tell if application has worked without issue.  Assuming during
development nothing appears to be slow Prometheus will not be used for
performance metrics.

Ideally the application should integrate with OpenTelemetry, but this is out
of scope for quick & dirty work that did not require production quality
observability.

## Operational instructions

Interactions with k8s are meant to be purposefully fragile.  If something
even smells strange, the tooling will stop and inform the user what seems
to be wrong.  In these cases, one needs to debug with `kubectl` what is
going on.  There is no standard answer to how to fix the service in all
situations, but at least you should

* Check the application logs
* Are metrics telling something useful
* Is there a blocking network policy
  * Note.  I know challenge did not specify network policy, and my helm
    stuff might not even have them.  Point of checking network policy is the
    history I have with them; more than few times it's been the network
    policy, to the point I am now very early on in all debug cases asking
    'are you sure it is not the network policy?'
* Is the deployment pending for a dependency, or in a restart loop?
* Have a look at `docker ps`, is the kindest/kind-control-plane container running?
* What is your computer doing, check `journalctl -b`

When nothing else helps, there is `make nuke-it-from-the-orbit` that will
wipe off all the things from k8s.  This is a last resort.

# UI and UX

The application is reachable from loopback with a browser.  If time allows,
there will be a very basic web UI that allows one to do the HTTP calls
graphically rather than with `curl`.  This comes with a strong promise
_not_ to deliver.

If UI is delivered mTLS certificate needs to be imported to certificate
store, which is a bit of a fiddly operation and different browsers /
operating systems need different instructions.  I am starting to feel this
feature creep is not happening.
